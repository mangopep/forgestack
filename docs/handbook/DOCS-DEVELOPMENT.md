# Working on the documentation site locally

Everything here should get a new contributor from clone to a running local docs site, with
generated references up to date and links validated, in about 10 minutes — excluding the time
`npm ci` takes to download packages the first time, which depends entirely on your connection.

## Requirements, exact versions

- **Go** — whatever version `go.mod` declares (check `go version` against it); needed for
  `cmd/docgen`, not for the website itself.
- **Node.js >= 22.12.0** — this is a real minimum, not a suggestion: the local search plugin's
  transitive dependencies (`cheerio`, `undici`) require it. `website/package.json`'s `engines`
  field states this. On an older Node (e.g. 20.x), `npm ci`/`npm install` still complete with
  `EBADENGINE` warnings — the build currently still works, but this is not guaranteed to stay
  true across future dependency updates, so don't rely on it.
- **npm** — whatever ships with your Node install; no separate pin needed.

## Installing dependencies

```bash
cd website
npm ci
```

`npm ci` (not `npm install`) installs exactly what `package-lock.json` specifies, deleting
`node_modules` first if it exists — this is what CI runs (`docs-check.yml`'s `website` job),
so running it yourself reproduces the same install CI gets.

## Starting the site locally

```bash
npm start
```

Opens a dev server with hot reload at `http://localhost:3000/` (not `/forgestack/` — that base
path only applies to the production build, matching GitHub Pages' project-page URL shape).

## Building the production site

```bash
npm run build
```

Output goes to `website/build/`. This is exactly what `docs-check.yml` (every PR, build-only)
and `pages-deploy.yml` (push to `main`, build-and-deploy) both run.

## Generating references and checking drift

From the repository root, not `website/`:

```bash
go run ./cmd/docgen generate all     # regenerate docs/generated/*.md from source
go run ./cmd/docgen check            # regenerate + diff + checklinks in one step
go run ./cmd/docgen checklinks .     # just the broken-relative-link check
```

`docgen check` is the local, pre-push equivalent of the required `docs` CI check — if it
passes locally, the CI job should too (same logic, same commands, just run by you instead of
by GitHub Actions).

## Validating diagrams

Mermaid diagrams (` ```mermaid ` code blocks) render **client-side only** — `npm run build`
succeeding and `go run ./cmd/docgen checklinks .` passing don't prove a diagram's syntax is
valid Mermaid, only that the page built. To actually check a diagram: `npm start`, navigate to
the page, and look at it. If a diagram shows a parse-error box instead of a chart, the Mermaid
syntax itself is wrong — this won't fail any CI check today, since nothing currently lints
Mermaid syntax independently of rendering.

## Troubleshooting common failures

- **`npm ci` reports `EBADENGINE`**: your Node is below 22.12.0. The install usually still
  completes; if something else then fails strangely, this is the first thing to check.
- **"Invalid sidebar file... these sidebar document ids do not exist"**: `website/sidebars.js`
  references a doc id that doesn't match an actual file. Docusaurus strips a leading numeric
  prefix from the filename when deriving the id (e.g. `adr/0001-go-kit-for-posts-module.md` →
  id `adr/go-kit-for-posts-module`) — if you add a new numbered file, use the stripped id in
  the sidebar, not the literal filename.
- **`onBrokenLinks: 'throw'` fails the build on a relative Markdown link**: this is the
  website's own build-time link check, separate from `docgen checklinks` — run the build
  locally to see exactly which file and link it means.
- **A page you added doesn't show up anywhere**: it exists under `docs/` but isn't referenced
  in `website/sidebars.js` — the sidebar here is manually curated (see
  `docs/adr/0003-documentation-as-code.md`), not autogenerated, so a new page needs an explicit
  entry.
- **Generated docs look stale in CI but `docgen check` passed locally**: you likely edited
  source after the last `generate all` without re-running it — `docgen check` only catches what
  exists on disk at the moment you run it.
