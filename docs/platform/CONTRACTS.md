# Language-independent service contracts

These are the conventions every ForgeStack reference service follows, implemented
independently in each language (no shared runtime library, no proprietary framework) —
just the same documented shape. Two services exist today: the Go API (`cmd/api`,
`internal/modules/posts`, `internal/platform`) and the Python API (`apps/python-api`).
This document is the contract; each service's own code is the implementation.

## Why independent implementations, not a shared library

A shared cross-language runtime library would itself become a dependency every future
service (Rust, TypeScript, an AI workload) would need to adopt or reimplement anyway —
that's a heavier, more proprietary commitment than documenting a convention each language
implements idiomatically. See "Extension guidance" below for what a new language needs to
provide to join this contract.

## 1. Service metadata and configuration

- Every service exposes its own name and version in its health response (see §2) — never
  a shared global registry, since that would be a single point of coupling between
  otherwise-independent services.
- Version defaults to the literal string `"dev"` for an unversioned local build — never a
  fabricated version number. Real builds set it explicitly (Go: `-ldflags
  "-X .../buildinfo.Version=..."`; Python: the `SERVICE_VERSION` environment variable,
  set in the Dockerfile).
- Configuration is validated at startup, not read ad hoc at call sites — a misconfigured
  deployment must fail fast and loud, not surface as a confusing runtime error later.
  Go: plain env var reads with explicit defaults (minimal surface today — see
  `docs/generated/CONFIG.md`). Python: `pydantic-settings`, which validates types/ranges
  before the app starts.

## 2. Health and readiness

Both services expose:

| Endpoint | Meaning | Response shape |
|---|---|---|
| `GET /healthz` | process is up and able to serve | `{"status": "ok", "service": "<name>", "version": "<version>"}` |
| `GET /readyz` | dependencies (if any) are reachable | `{"status": "ready", "storage": "in-memory"}` |

Neither service has an external dependency yet (both use in-memory storage), so `/readyz`
today is equivalent to `/healthz` in practice — the distinction exists so that adding a
real dependency (a database, a queue) later only changes what `/readyz` checks, not the
contract's shape or the fact that both endpoints already exist.

## 3. HTTP errors and API versioning

Every error response is a JSON object shaped `{"error": "<human-readable message>"}` —
never a stack trace, an internal error type name, or a driver/library error message. An
unclassified/unexpected exception always maps to a generic `"internal error"` string;
only errors explicitly marked as client-caused (Go: `apierror.Bad`; Python: a raised
`HTTPException` or a Pydantic validation failure) get a specific message back.

**One documented, deliberate difference, not an inconsistency to "fix"**: the Go API
returns `400 Bad Request` for a client input error; the Python API returns FastAPI's
native `422 Unprocessable Entity` for a request-validation failure. The *response body
shape* is the shared contract (`{"error": "..."}`); the exact status code for "the client
sent something syntactically parseable but semantically invalid" is left to each
framework's own idiom rather than forced into artificial uniformity.

API versioning: both services prefix resource routes with `/api/v1/` (health/readiness
routes are intentionally unversioned — they're operational signals, not part of the
versioned resource API). A future `v2` would add new routes under `/api/v2/`, not mutate
`v1`'s behavior.

## 4. OpenAPI contract compatibility

- **Python**: FastAPI auto-generates a real OpenAPI document at `/openapi.json` (and an
  interactive UI at `/docs`) from the Pydantic schemas already used for validation — no
  separate spec to keep in sync by hand.
- **Go**: no hand-authored OpenAPI document exists yet. `docs/generated/API.md`
  (generated by `cmd/docgen` directly from `internal/platform/router/router.go`'s route
  registrations) is today's source of truth for the Go API's routes — accurate because it
  cannot drift from the code (CI fails the build if it does), unlike a hand-maintained
  spec file. Writing a real OpenAPI document for the Go API, generated from the same
  source rather than hand-authored in parallel, is a reasonable future addition — not
  done here to avoid introducing a second, potentially-drifting source of truth for the
  same information this phase's time budget didn't allow verifying stays accurate.

## 5. Logging and correlation IDs

Every request carries a correlation ID via the `X-Request-Id` header: if the caller
supplies one, it's reused (so a request can be traced across multiple services); if not,
one is generated. The ID is echoed back on the response and attached to every log line
produced while handling that request.

- **Go**: `internal/platform/middleware.CorrelationID`, attached via `context.Context`,
  included in `slog` log lines as the `request_id` field.
  Generated with `crypto/rand` (16 random bytes, hex-encoded) — not a UUID library, to
  avoid an extra dependency for "a unique-enough trace token."
- **Python**: `app.middleware.CorrelationIDMiddleware`, attached via a `contextvars.ContextVar`
  (the async equivalent of Go's context value), included in every JSON log line's
  `request_id` field by `app.logging_config.JSONFormatter`. Generated with
  `secrets.token_hex(16)` — the same 16-byte-hex shape as Go's, though the two are
  generated independently, not from a shared function.

Both emit one JSON log line per request (`http_request`: method, path, status,
duration_ms, request_id) — same fields, independently implemented (Go: a custom `slog`
call; Python: a ~20-line stdlib `logging.Formatter`, deliberately not a third-party
structured-logging library, since the stdlib already covers what this service needs).

## 6. Operational signals and lifecycle

- **Startup**: both services log a `"service starting"` line before accepting traffic.
- **Graceful shutdown**: on `SIGINT`/`SIGTERM`, in-flight requests are allowed to
  complete before the process exits.
  - Go: `net/http.Server` has no built-in signal handling, so `cmd/api/main.go` wires
    `signal.NotifyContext` + `Server.Shutdown(ctx)` with a 10-second grace period
    explicitly.
  - Python: `uvicorn` already handles `SIGINT`/`SIGTERM` this way out of the box — the
    `lifespan` hook in `apps/python-api/app/main.py` only logs the transition, it does
    not need to reimplement shutdown handling uvicorn already provides.
- **Request body limits**: both services reject an oversized request body before fully
  reading it. Go: `middleware.MaxBytes` (4096 bytes, via `http.MaxBytesReader`). Python:
  `MaxBodySizeMiddleware` checks `Content-Length` against the same 4096-byte default
  (configurable via `REQUEST_BODY_MAX_BYTES`) before the body is read.
- **Timeouts**: the Go API sets explicit `ReadHeaderTimeout`/`ReadTimeout`/
  `WriteTimeout`/`IdleTimeout` on its `http.Server` (no such equivalent needed for
  Python yet — `uvicorn` applies its own sane server-level timeouts; revisit if a real
  outbound dependency, with its own timeout/retry needs, is added later. **Bounded
  retries**: neither service has an outbound network dependency yet (both are
  in-memory-only), so there is nothing to retry — this section will gain real content
  the moment one is added, not before, since a retry policy for a dependency that doesn't
  exist would be invented, not verified.

## 7. Optional module integration

Both services demonstrate the same shape for adding a new resource:
1. A typed schema (Go: a `domain` package; Python: a `pydantic.BaseModel` in
   `schemas.py`).
2. A storage interface with an in-memory implementation (Go:
   `repository.NewInMemory()`; Python: `InMemoryItemStore`) — swappable behind that
   interface later without touching the transport layer.
3. A transport/router layer that wires the resource's routes into the service's single
   composition root (Go: `internal/platform/router.New()`; Python:
   `app.routers.items.router`, included via `app.include_router(...)` in
   `app/main.py`).

Neither service introduces a plugin system, a service registry, or a dependency-injection
container beyond what each framework already provides natively — see "Extension
guidance" below for what adding an entirely new *service* (not just a new resource
within an existing one) requires.

## Extension guidance: adding a new language or service

A new service (Rust, TypeScript, a frontend client, an AI workload) joins this contract
by implementing, in whatever way is idiomatic for that language/framework:

1. `GET /healthz` and `GET /readyz` with the exact response shapes in §2.
2. `{"error": "<message>"}` for every error response (§3) — the status code can follow
   the framework's own idiom, the body shape cannot.
3. An `X-Request-Id` request/response header, reused if present, generated if absent (§5).
4. A startup/shutdown log line and graceful handling of `SIGINT`/`SIGTERM` (§6).
5. Its own `Dockerfile` (multi-stage, non-root, pinned base image and dependency
   versions) and an entry in `compose.yaml`, following this repo's existing services as
   examples rather than inventing a new pattern.

Nothing here requires AI-specific tooling, a message broker, Kubernetes, or an
observability stack — those are later phases (F8, F9, F11+) and are out of scope for a
service that only needs to satisfy this contract.

## Known limitations, not hidden

- No real OpenAPI document exists for the Go API yet (see §4).
- No distributed tracing (OpenTelemetry) exists yet — the correlation-ID contract in §5
  is the deliberately lightweight foundation that a real tracing system would build on
  top of later (F8), not a replacement for one.
- Neither service has rate limiting, authentication, or a real (non-in-memory) datastore
  — all explicitly out of scope for F3 per the mission's own constraints.
