# ADR 0003: Documentation-as-code architecture and publishing

- Status: Implemented locally (this branch); publishing to GitHub Pages is a separate,
  already-existing, main-only workflow — not re-approved or changed by this ADR.
- Date: 2026-11-13

## Context

F2 asked for "a production-quality, automated, version-controlled documentation system."
Auditing first (per working protocol) found that most of the foundation already existed from
earlier work: a Docusaurus site pointing directly at `docs/` (no content duplication),
`cmd/docgen` generating deterministic references from source, `docs-check.yml` enforcing
staleness/broken-link checks as a required `docs` status check, and `pages-deploy.yml`
publishing only from `main`. This ADR records what F2 added on top of that foundation and why,
rather than re-deciding settled questions.

## Decision 1: one source of truth, never two

The website's `docs` plugin is configured with `path: '../docs'` — it renders the repository's
real `docs/` directory, not a copy inside `website/`. This was already true before F2 and is
reaffirmed, not changed: every new page this ADR's work added (`docs/architecture/*.md`,
`docs/adr/0003-*.md`) lives under `docs/`, the same place `docgen`'s staleness checks look.
There is exactly one place to edit any given piece of documentation.

## Decision 2: sidebar organization without moving files

The prior sidebar was `{ type: 'autogenerated', dirName: '.' }` — a flat reflection of
whatever folders happen to exist under `docs/`. F2 replaces it with a manually curated
`sidebars.js` organized into the 12 categories the mission specified (Getting Started,
Architecture, Applications, Platform, Git & CI/CD, Infrastructure, Deployment, Security,
Observability, Labs, Operations, Contributing), **without moving any existing file**. Every
sidebar entry references an existing doc by its id (relative path, no extension); nothing was
relocated, so every existing link (including any bookmarked or linked from elsewhere) keeps
working. This directly satisfies "preserve existing links... when moving documents" by not
moving anything in the first place — the simpler, lower-risk option when it's available.

## Decision 3: honest status labeling over a complete-looking site

Several of the 12 categories (Observability, Labs) have no implemented content yet — only
roadmap entries. Rather than fabricate pages describing capabilities that don't exist, or
silently omit those categories from the sidebar, each has one short page stating plainly
**Status: Planned**, with a pointer to the roadmap module that will build it. Every new
architecture diagram page added by this ADR's work states explicitly at the top whether it
documents something **implemented**, **planned**, or **not verified** — this repo's existing
"never claim production readiness without evidence" principle, applied to diagrams
specifically, since a diagram is easy to make look more finished than the thing it depicts.

## Decision 4: extend `docgen`, don't duplicate its approach

Two new generators (`internal/docgen/generate_commands.go`,
`internal/docgen/generate_config.go`) follow the exact pattern `generate_api.go`/
`generate_ci.go` already established: parse real source (the Makefile's `.PHONY` targets;
every `os.Getenv`/`os.LookupEnv` call found via `go/ast`), render deterministic Markdown with a
"do not edit by hand" header, write under `docs/generated/`. A new `docgen check` command
wraps `generate all` + `git diff --exit-code` + `checklinks` in one call — the same sequence
`docs-check.yml` already runs in CI, now also runnable locally before pushing, so a
contributor finds staleness before the required check does.

## Decision 5: no change to what's already enforced or how it's enforced

`docs-check.yml`'s required-check context name (`docs`) is unchanged. `pages-deploy.yml`'s
`push: branches: [main]` trigger, its scoped permissions (`contents: read, pages: write,
id-token: write`), and its concurrency group are unchanged. F1's branch-promotion rulesets are
unaffected — this work only adds documentation content and two new, non-destructive local
`docgen` subcommands; it does not touch any `.github/workflows/*.yml` trigger, permission, or
required-check list.

## Known limitation, recorded not hidden

Adding the local-search plugin (`npm install`) surfaced that `website/package-lock.json`
already carried 26 known vulnerabilities (16 critical) in Docusaurus's own dev-tooling
transitive dependencies (`webpack-dev-server`, `tinypool` — used for `docusaurus start`, not
the production build) — confirmed present in a clean `npm ci` of the pre-existing lockfile,
before any F2 change. This predates F2 and is out of scope to fix here (likely requires a
Docusaurus major-version bump, its own reviewable change); recorded so it isn't mistaken for
something this work introduced, and so it isn't silently lost either.

## Consequences

- New: `docs/architecture/PLATFORM-OVERVIEW.md`, `CI-CD-FLOW.md`,
  `APPLICATION-ARCHITECTURE.md`, `INFRASTRUCTURE-OWNERSHIP.md`, `SECURITY-TRUST-BOUNDARIES.md`
  — 8 of the 9 required diagrams (the 9th, git-flow, already existed in
  `docs/handbook/BRANCHING.md` and is linked from the sidebar rather than duplicated).
- New: `docs/generated/COMMANDS.md`, `docs/generated/CONFIG.md`, both deterministic and
  tested.
- New: `website/sidebars.js` reorganized into the 12-category IA.
- New: local search (`@easyops-cn/docusaurus-search-local`, build-time index, no paid SaaS).
- No workflow file's trigger, permission, or required-check name changed.
