# Control & evidence registry

**Status: implemented (evidence foundations only)** — this is the F4 "Audit & Trust" module's
foundation layer. See `docs/ROADMAP.md`'s "Audit & Trust" section for what's planned beyond
this (F5-F10, and a future customer-facing Trust Center) and not yet built.

## What the registry actually is

Two files, not a database or a service:

- **`docs/security/findings-register.json`** — hand-maintained, human-reviewed. One entry per
  tracked exception/finding, each with severity, affected component, fixed version (or "none
  available" with evidence), exploitability context, environment, **owner**, evidence,
  remediation plan, and **review date**. Updated in the same PR that changes an exception's
  scope.
- **`secreport.json`** (generated by `cmd/secreport`, not committed — produced fresh by CI or
  on demand locally) — machine-generated, versioned (`schema_version`), linked to
  **product/environment/owner/commit/branch**, built entirely from real scanner output. Every
  entry carries a `control_type`: `automated` (a scanner actually verified it) or `manual` (a
  human reviewed and accepted a tradeoff a scanner can't approve) — see "Manual vs. automated
  controls" below.

They're deliberately kept separate and cross-referenced by issue number/ID rather than merged
into one system: the hand-maintained register is slow-changing, reviewed, authoritative
context; the generated report is fast-changing, reproducible, point-in-time evidence.

## Explicit states, never fabricated

`cmd/secreport`'s `OverallStatus` is always one of exactly these — see
`internal/secreport.computeOverallStatus` and its tests for the precedence rules:

| State | Meaning |
|---|---|
| `PASS` | every tool ran, no unresolved HIGH/CRITICAL findings, no expired exceptions |
| `FAIL: ...` | an unresolved (non-suppressed) HIGH/CRITICAL finding exists |
| `EXPIRED: ...` | a tracked exception's review date has passed |
| `MISSING: ...` | a required tool's evidence is missing or unreadable |
| `NOT_VERIFIED: ...` | evidence is clean, but a capability hasn't been independently verified on live infrastructure (e.g. the keyless signing flow — see `docs/architecture/SUPPLY-CHAIN-SECURITY.md`) |

**The report can never silently report `PASS` while hiding a `MISSING`, `EXPIRED`, or
`FAIL` condition** — this is enforced in code (not just documentation) and covered by
dedicated tests in `internal/secreport/report_test.go`.

## Manual vs. automated controls

Every `Finding` and `Exception` the registry/report tracks carries a `control_type`:

- **`automated`** — a scanner (govulncheck, pip-audit, Trivy, gitleaks, npm audit) actually
  ran and produced this result. Reproducible by anyone, any time, from
  `docs/security/VULNERABILITY-LIFECYCLE.md`'s local commands.
- **`manual`** — a human reviewed and accepted something a scanner alone cannot decide (e.g.
  "this npm finding is build-tooling-only, confirmed by inspecting what ships in
  `website/build/`"). Exceptions default to `manual` for exactly this reason.

Conflating the two would let an unverified manual claim borrow the credibility of a real
automated check — F4's own instruction is explicit about this, and the schema enforces the
distinction rather than relying on a reader to remember it.

## Generating an audit-ready report locally

```bash
# 1. Run the real scanners (see VULNERABILITY-LIFECYCLE.md's "Local reproduction" for every
#    command in full) and save their output.
# 2. Assemble the report:
go run ./cmd/secreport \
  -product forgestack -environment local -owner "<you>" \
  -govulncheck govulncheck.json -pip-audit pip-audit.json \
  -trivy-go-image trivy-go-image.json -trivy-python-image trivy-python-image.json \
  -gitleaks gitleaks-report.json -npm-audit npm-audit.json \
  -npm-audit-baseline website/.security/npm-audit-baseline.json \
  -json-out secreport.json -md-out secreport.md -vex-out vex.json
```

This produces `secreport.json` (machine-readable, stable schema), `secreport.md` (human-
readable summary — the same content CI posts to a run's job summary), and `vex.json`
(OpenVEX-shaped per-CVE assessment). None of these are a PDF audit package — F4 deliberately
did not build a document-generation pipeline on top of this (see "Do not build a large
reporting microservice" in the F4 scope) because no real need has justified it yet.

## Retention, access, and what this is *not*

See `docs/architecture/SUPPLY-CHAIN-SECURITY.md`'s "SBOM and artifact retention, access, and
sharing" section — stated once, not duplicated here. In short: GitHub Actions artifact
storage, 90-day retention, ordinary repository access control. Not an immutable audit trail,
not a customer-facing sharing portal (that's the deferred Trust Center work).
